# Follow-up review: uncertain starts and persisted input

Reviewed baseline: `6e3696a1e6e4457a0b8264a4bd6edf8a939d7638`, PR #1.

## Reproduced and fixed

1. An accepted asynchronous `start()` with delayed process visibility was issued again on every reconciliation, including after controller restart. A persisted STARTING intent now waits closed without another start. A crash between intent persistence and the actual call intentionally requires explicit recovery rather than guessing whether the side effect happened.
2. Explicit recovery from STARTING/ERROR calls the new trusted `Backend.fence_pending_starts()` before observation/retry. The adapter must cancel or settle all accepted older requests and guarantee they cannot start a delayed second backend. Failure stays ERROR/closed. An empty process inventory is not such a guarantee. This API remains an implementation requirement for the future production adapter, not a claim that Docker fencing is installed.
3. Persisted state now rejects unknown/inconsistent phase/gate/goal combinations, invalid operation UUIDs/revisions, boolean schema versions and duplicate JSON keys. Reads are bounded, use O_NOFOLLOW, and reject non-regular files and dangling symlinks. Malformed state raises before backend mutations; proxy consumers must independently fail closed when state is invalid or stale.
4. A pinned ZIP with `map.json\0hidden` was accepted because ZipInfo silently truncates `filename`. The validator now checks `orig_filename` and rejects the noncanonical original path before reading member data. The regression uses matching outer/member hashes; checksums do not replace path validation.
