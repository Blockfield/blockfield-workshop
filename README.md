# Мастерская Blockfield

Контроллер постоянной мастерской рядом с Game и проверка кандидатов карт. Исходники выделены из `blockfield-server/tools/workshop`
с историей; исходная история сервера сохранена.

## Разработка

Нужны Python 3.12+, Node.js 22 и just 1.57.0. Без mise и глобальных установок.

```sh
just setup
just check
just format
just python workshopctl.py --help
```

Linux проверяет весь контроллер. Windows проверяет переносимые ZIP-validator
и journal; production-controller требует Linux, Docker Swarm и `flock`.
Запуск стенда — только через workspace и с проверкой владельцев процессов.

## Образ и интеграция

Отдельного образа у мастерской нет. Сервис `blockfield-workshop` в Dokploy использует тот же серверный образ с
`BLOCKFIELD_PROFILE=workshop`; WorldEdit сервер добавляет сам в этом профиле.
Game и мастерская работают одновременно, каждый с собственными данными и mutex.
Контроллер управляет только мастерской: обычная игра и её кампании продолжаются
во время смены редакторской сессии, снимка карты или проверки кандидата.

Перед запуском редактора контроллер берёт точный immutable image работающего Game.
После нового готового выпуска Game он сохраняет и обновляет стабильный редактор,
сохраняя его сессию и черновики. Проверка кандидата и незавершённая операция откладывают
обновление; новый клиент выпускается только после совместимой готовности обоих backend.
У мастерской постоянно одна replica; при обслуживании перезапускается только она.
Готовность и ACL прокси проверяет отдельно для Game и мастерской.

Кандидаты ZIP используют Python 3.12.14 / zlib 1.3.2; неверный compressor
останавливает snapshot до закрытия входа. `just` и systemd используют pinned Python.
Контроллер остаётся host-systemd service: запускать второй controller в контейнере нельзя.
На хост он ставится из checkout этого репозитория (см. OPERATIONS).

[Операции и протокол файлов](docs/OPERATIONS.md), [systemd](systemd/),
[изолированный E2E](e2e/README.md). Публикация карт и пины находятся
в [blockfield-server/scripts/maps](https://github.com/Blockfield/blockfield-server/tree/main/scripts/maps);
server получает validator и map IDs по полному SHA и checksum.
Исторические архивные релизы не изменяются.

Карты используют поведение Git поверх существующего хранилища SHA256: именованные ветки,
последовательные коммиты и неизменяемые запросы на обзор. Сессия закрепляет ветку каждой карты;
смена ветки создаёт отдельную копию и сохраняет старые правки. Слияние в защищённую `main`
проверяет ожидаемый коммит и требует явного выбора при конфликтах регионов. Восстановление
старой карты создаёт новый коммит, сохраняя всю историю. Реальный Git-репозиторий для миров не нужен.

Host CLI поддерживает `branch-create`, `commit`, `compare` и `merge-preview`; для выбора веток
используйте `request workshop --session <новый-UUID> --maps <mapId> --branches <mapId>=<branch>`.
Подробные поля, права и примеры находятся в [OPERATIONS](docs/OPERATIONS.md).

Через интерфейс можно создать новую арену с нуля для `campaign`, `room`, `tdm`, `snipers`,
`awp`, `deathmatch` и `training`: контроллер создаёт пустой мир с небольшой стартовой
платформой и отдельный частный черновик. Незавершённая карта остаётся без `main`;
разметка выбранных режимов проверяется перед обзором, тестом и публикацией.
Переименование меняет выбранный черновик. Проверка запускает замороженный коммит
в выбранном поддерживаемом режиме, сохраняя Game и прежние редакторские сессии.
